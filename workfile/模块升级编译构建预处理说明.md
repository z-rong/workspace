# 模块升级编译构建预处理说明

## 一、约束与限制

1. 当前模块升级能力仅支持 SystemAbility 的升级，独立库形态由于加载依赖机制不同，目前待规划支持。

2. 仅预制到版本中的模块才允许升级，禁止新增模块升级。

   例如：必须是预制到 `/system/module_update` 目录下的模块包才允许升级，不在此目录下的模块包是不会升级的。

3. 当前仅支持模块包升级本地安装和调试，暂未支持云端连接和升级包下载。

## 二、新增模块包主要步骤

第一次生成模块升级包，需要进行各种预处理，需要新增或更新相关配置文件，主要步骤参考如下：

### 1. 梳理模块包依赖

梳理模块及其依赖，依赖要尽可能少，且依赖链上的要以ABI兼容的模块结尾。这其中可能还涉及到ABI不兼容的库改造为ABI兼容的库的工作。声明一个二进制对外的ABI兼容是通过在编译脚本中加上 `stable = true` 来声明的。

```shell
ohos_shared_library("LibraryX") {
  ......
  stable = true
  ......
}
```

### 2. 添加模块升级属性 `module-update`

修改模块升级包对应的SA所在进程的对应 cfg 配置文件，在其所在 service 属性中添加 `"module-update" : 1 `，否则不生效。

```shell
"services" : [{
    ......
    "module-update" : 1                // 模块升级属性，配置为1则生效，默认不生效
    ......
}
```

### 3. 编写gn模板，打包编译模块包和HMP包

### 4. 本地调试，验证模块包是否升级成功功能是否正常

## 三、模块包编译模板和配置文件

模块升级提供了两个编译模板，模块开发者可以通过在gn中使用编译模板并执行编译命令对该模块进行打包和签名。

### 1. 模块包配置

#### 1.1 `ohos_module_package` 模板

模块包使用编译模板`ohos_module_package`对单模块进行编译打包以及签名。

- **模板字段详细说明：**

| 模板字段        | 含义                         | 赋值               | 必选 |
| :-------------- | :--------------------------- | :----------------- | :--- |
| libraries       | 二进制库集合                 | 二进制库目标target | 否   |
| binaries        | 可执行文件集合               | 可执行目标target   | 否   |
| prebuilts       | 预编译文件集合               | 预编译目标target   | 否   |
| etc             | 配置文件集合                 | 配置目标target     | 否   |
| module_config   | 指定模块配置文件config.json  | 文件路径           | 是   |
| zip_private_key | zip包签名私钥                | 文件路径           | 是   |
| sign_cert       | zip包签名证书                | 文件路径           | 是   |
| img_private_key | 镜像HVB签名私钥              | 文件路径           | 否   |
| img_public_key  | 镜像HVB签名公钥              | 文件路径           | 否   |
| empty           | 是否打包成空包，默认不打空包 | true or false      | 否   |
| part_name       | 部件名                       | 部件名             | 是   |
| subsystem_name  | 子系统名                     | 子系统名           | 是   |

- **gn 编译模板示例：**

```shell
import("//build/templates/update/module_update.gni")
ohos_module_package("wms_package") {
  libraries = [
    ":libwms",
  ]
  etc = [
    "//foundation/window/window_manager/sa_profile:wms_sa_profile",
  ]
  module_config = "config.json"
  zip_private_key = "key/rsa_private_key2048.pem"
  sign_cert = "sign_cert/signing_cert.crt"
  img_private_key = "key/test_priv.pem"
  img_public_key = "key/test_pub.pem"
  part_name = "window_manager"
  subsystem_name = "window"
}
```

#### 1.2 配置文件（config.json）

- **模板字段详细说明：**

| 配置项  | 含义                 | 规范                       |
| :------ | :------------------- | :------------------------- |
| name    | 升级模块（SA）的名称 | 与系统SA名称保持一致       |
| id      | 升级模块（SA）的id   | 与sa_profile配置id保持一致 |
| version | 升级模块版本号       | a.v.p格式                  |

- **配置文件（config.json）模板示例：**

```plain
{
  "name": "sa_name",
  "id": sa_id,
  "version": "a.v.p"
}
```

## 四、模块升级完整示例

以 `//foundation/window/window_manager/wmserver:libwms` 模块进行模块升级示例。

### 1. 梳理 `libwms` 模块包以及依赖

在模块包以及依赖的编译模板中加上 `stable = true`字段，以声明二进制对外的ABI是兼容的。

```shell
ohos_shared_library("libwms") {
  ......
  stable = true
  ......
}
```

### 2. 添加模块升级属性 `"module-update" : 1`

找到`libwms` 模块包对应 SA 所在进程(即foundation进程)的 cfg 配置文件(即`//foundation/systemabilitymgr/safwk/etc/profile/foundation.cfg`)，在 name 是 foundation 的 services 中添加模块升级属性字段：`"module-update" : 1`

```shell
"services" : [{
             "name" : "foundation",
             ......
             "module-update" : 1,
             ......
}]
             
```

`module-update`：模块升级属性，配置为 1 则生效，默认不生效。

### 3. 新增模块升级打包编译模板

在 `//foundation/window/window_manager/wmserver/BUILD.gn` 文件中追加类似以下内容进行编译打包：

```shell
ohos_module_package("wms_package") {
  libraries = [
    ":libwms",
  ]

  etc = [
    "//foundation/window/window_manager/sa_profile:wms_sa_profile",
  ]
  module_config = "config.json"
  zip_private_key = "rsa_private_key2048.pem"
  sign_cert = "signing_cert.crt"
  # img_private_key = "key/test_priv.pem"
  # img_public_key = "key/test_pub.pem"
  part_name = "window_manager"
  subsystem_name = "window"
}
```

###  4. 新增配置文件 config.json

在 `//foundation/window/window_manager/wmserver` 目录下分别新增 config.json 文件，内容参考如下：

- config.json 文件内容：

```shell
{
  "name": "wms",
  "id": 4606,
  "version": "1.0.1"
}
```

### 5. 拷贝签名证书和私钥

将生成的 `signing_cert.crt` 和 `rsa_private_key2048.pem`  文件拷贝到 `//foundation/window/window_manager/wmserver` 目录下。

### 6. 更新 bundle.json 文件，加入编译依赖

将 `demo_hmp` 标识符添加到 `//foundation/window/window_manager/bundle.json` 文件中，以进行打包编译生成模块包文件。

```shell
# //foundation/window/window_manager/bundle.json
{
	......
    "component": {
      "name": "window_manager",
      "subsystem": "window",
      ......
      "build": {
        "group_type": {
          ......
          "service_group": [
            ......
            "//foundation/window/window_manager/wmserver:wms_package",
            ......
          ]
        },
        ......
      }
    }
}
```

### 7. 拷贝模块包的ABI兼容文件

新增模块包时第一次编译会因为 `//prebuilts/abi_dumps/ohos_clang_arm/` 目录下没有对应模块包的ABI兼容文件(一般是以`_abi_info.dump`为后缀的文件)而报错无法通过编译，此时需要在第一次编译时生成的模块包ABI兼容文件手动拷贝到`//prebuilts/abi_dumps/ohos_clang_arm/` 目录下，若目录不存在则需要手动创建。

模块包的ABI兼容文件一般会生成在模块对象编译临时输出目录下，例如：`//out/设备名/obj/模块对象编译临时文件输出目录/`

可以通过在 `//out/设备名/obj/` 目录下执行类似以下命令查找模块包的ABI兼容文件：

```shell
# 通过类似以下的命令查找ABI兼容文件
# cd //out/设备名/obj/
find . -name `模块标识`_abi_info.dump
```

执行类似以下的命令拷贝ABI兼容文件

```shell
# 源码根目录下执行类似以下命令
mkdir -p prebuilts/abi_dumps/ohos_clang_arm/
cp out/khdvk_rk3568_a/obj/foundation/window/window_manager/wmserver/libwms_abi_info.dump prebuilts/abi_dumps/ohos_clang_arm/
```

### 8. 编译生成模块包

再次编译生成模块包，编译后的模块包文件在一般在类似以下路径中：

`//out/设备名/obj/模块编译临时文件输出目录/module_package/zip_output/模块包名.zip`

例如：`//out/设备名/obj/foundation/window/window_manager/wmserver/module_package/zip_output/wms_package.zip`

### 9. 上传模块升级包到预制目录(仅新增模块包时需要，否则可跳过)

新增模块包时需要将模块包放到 `/system/module_update/模块包名` 目录下，否则无法正常升级。仅第一次新增模块包时需要执行此操作，后续更新时不需要执行此操作。

- 创建预制目录

```shell
# 连接开发板，重新挂载根目录
mount -o rw,remount /
# 创建模块包的预制目录
# mkdir -p /system/module_update/`模块包名`
mkdir -p /system/module_update/wms_package
```

- 通过 hdc 工具将模块包 `wms_package.zip`  上传到 `/system/module_update/wms_package` 目录下
- 修改文件权限所属

```shell
chown -R update:update /system/module_update/wms_package
```

### 10. 上传模块包至升级目录

- 创建相关目录

  若目录已存在可跳过

```shell
# mkdir -p /data/module_update/active/`模块包名`/
# mkdir -p /data/module_update_package/`模块包名`/
# 示例：
mkdir -p /data/module_update/active/wms_package/
mkdir -p /data/module_update_package/wms_package/
```

- 通过 hdc 工具将模块包 `wms_package.zip`  上传到 `/data/module_update_package/wms_package/`

  若目录下已存在模块包，需要先删除再上传。

- 修改文件权限所属

```shell
# chown -R update:update /data/module_update/active/`模块包名`/
# chown -R update:update /data/module_update_package/`模块包名`/
# 示例：
chown -R update:update /data/module_update/active/wms_package
chown -R update:update /data/module_update_package/wms_package
```

### 11. 重启开发板并验证模块功能

重启开发板后，模块包会自动挂载运行在 `/module_update/模块包id` 目录下。

- 在开发板上执行类似以下命令，查看模块包版本号是否发生变化

```shell
# cat /module_update/`模块包id`/config.json
# 示例：
cat /module_update/4606/config.json
```

- 验证模块包功能运行是否正常

**模块包运行优先级顺序**

1. **升级模块包**(/data/module_update_package目录下的模块包) > **预制模块包**(/system/module_update目录下模块包) > **默认的模块包**
2. 若预制模块包不存在，则无论升级模块包是否存在，都运行默认的模块包
3. 若没有在`/data/module_update/active` 目录下创建模块包目录，则无论升级模块包是否存在，则都不会运行升级模块包

### 12. 卸载

执行类似以下的命令移除模块包文件，然后重启开发板，验证模块包是否卸载成功。

```shell
# rm -rf /data/module_update/active/`模块包名`/`模块包名`.zip
# rm -rf /data/module_update_package/`模块包名`/`模块包名`.zip
rm -rf /data/module_update/active/wms_package/wms_package.zip
rm -rf /data/module_update_package/wms_package/wms_package.zip
```

### 运行时错误：SELinux校验失败

问题现象：

升级失败，hilog中报错了相关的SELinux权限校验失败的日志。



可能原因：

未配置相应的SELinux权限。



解决措施：

使能模块升级的SA进程需要配置相应的SELinux权限，才能在SA启动时从升级目录加载so库。举例如下：

```plain
allow foundation module_update_file:dir { search };
allow foundation module_update_file:file { open read getattr };
allow foundation module_update_lib_file:dir { search };
allow foundation module_update_lib_file:file { open read getattr map execute };
```

由于模块升级相关权限已被最小化管控，SA进程还需要在以下neverallow规则中配置例外才能使上面配置的权限生效：

```plain
# sa process which support module update should add itself here
neverallow { domain -init -module_update_service -foundation debug_only(`-hdcd -sh') } { module_update_file
  module_update_bin_file module_update_lib_file }:{ file dir } *;
```



### 编译失败：log中报错依赖的Python库asn1crypto或cryptography找不到

问题现象：

编译失败，编译日志中提示asn1crypto或cryptography找不到。



可能原因：

未安装Python依赖的asn1crypto或cryptography库。



解决措施：

执行build下的prebuilts_download.sh：

```
bash build/prebuilts_download.sh
```
