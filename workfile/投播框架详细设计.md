# 一、总体介绍
## 1 简介
### 1.1 背景
日益增长的媒体业务需求对多媒体子系统服务能力提出了挑战。当前多媒体子系统提供了音频、视频、相机、媒体库等基础软件服务能力，但缺少流媒体协议的接入与接出和流媒体数据的转发能力。因此需一款媒体数据获取、处理、输出与播放的框架，在此框架之上能够实现高效开发，并且满足高性能和可扩展要求。
### 1.2 设计目标 

- 具备任意一种流媒体协议的接入；
- 具备任意一种流媒体协议的接出；
- 具备任意一种流媒体数据的转发；
- 具备任意一种媒体源接入；
- 具备任意一种媒体源播放；
- 具备任意一种媒体源流转；
- 具备支持多应用并发能力；
- 具备跨进程交互能力；
- 具备云平台监控能力；
- 具备服务数据上报能力；
- 支持标准协议及自定义协议扩展；
- 支持多路流混屏播放；
- 支持多路流合并转发；
- 支持多实例播放窗口；
### 1.3 支持能力
#### 1.3.1 投屏能力

- 具备多端设备向同一个OS设备投屏（m：1）；
- 具备OS设备向不同的设备投屏（1：1）；
- 具备OS设备向不同的设备投屏同一个流（1：n）；
- 具备OS设备将接收的投屏数据再转投到另一台设备；
- 具备将本地文件播放源投屏到其他设备；
- 具备将分布式摄像头数据投屏到其他设备；
- 具备本地屏幕数据投屏到其他设备；
- 具备将本地摄像头数据投屏到其他设备；
- 具备将通过流媒体协议拉取的数据投屏到其他设备；
#### 1.3.2 流转能力

- 具备多端设备向同一个OS设备流转（m：1）；
- 具备OS设备向不同的设备流转（1：1）；
- 具备OS设备向不同的设备流转同一个流（1：n）；
- 具备OS设备将接收的流转数据再流转到另一台设备；
- 具备将本地文件播放源流转到其他设备；
- 具备本地屏幕数据流转到其他设备；
- 具备将分布式摄像头数据流转到其他设备；
- 具备将本地摄像头数据流转到其他设备；
- 具备通过流媒体协议拉取的数据流转到其他设备；
- 具备通过分布式软总线作为音视频流转的数据通道；
#### 1.3.3 混流能力

- 具备不同视频源多轨合流发送能力；
- 具备不同音频源多轨合流发送能力；
- 具备接收复合流处理能力；
#### 1.3.4 窗口播放能力

- 具备多窗口播放实例能力；
- 具备窗口2|4|9宫格合流播放能力；
- 具备多协议拉流播放能力；
- 具备本地媒体文件播放能力；
- 具备本地摄像头播放能力；
- 具备分布式媒体资源播放能力；
- 具备多视频帧混合能力；
- 具备多音频帧混合能力；
#### 1.3.5 拉流能力

- 具备使用流媒体协议拉流能力，如RTSP、RTMP、WEBRTC、SRT、GB28181等；
- 具备使用分布式软总线拉流能力；
- 具备使用私有协议拉流能力；
#### 1.3.6 推流能力

- 具备使用流媒体协议推流能力，如RTSP、RTMP、WEBRTC、SRT、GB28181等；
- 具备使用分布式软总线推流能力；
- 具备使用私有协议推流能力；
### 1.4 扩展能力
#### 1.4.1 投屏能力扩展
扩展DLNA方案相关的协议支持；
#### 1.4.2 流媒体协议扩展
扩展其他流媒体协议的拉流与推流，如RTSP、RTMP、WEBRTC、SRT、GB28181等。

- 支持RTSP，监控设备拉流和推流的通用方式；
- 支持RTMP，公有云推流和拉流的常见方式；
- 支持WEBRTC，OS设备可以接收浏览器的推流，也可以向浏览器发流；
- 支持SRT，广电和直播行业互联网化；
- 支持GB28181，监控和智能家居行业互联网化；
- 支持分布式软总线，基于OS设备间的流传输和消息传输；
- 支持私有协议，定制音视频源传输方式；
- 扩展分布式文件、分布式屏幕流转到其他设备；
#### 1.4.3 平台下发能力扩展
待有该业务需求后补充。
#### 1.4.4 上报平台能力扩展
待有该业务需求后补充。
#### 1.4.5 编码能力扩展
待芯片能力提升后补充。
#### 1.4.6 分布式能力补充
分布式软总线子系统提供软总线能力，基于软总线衍生出分布式屏幕、分布式相机等服务。因此鸿蒙系统具备鸿蒙设备间的投屏和相机流转功能。
多媒体子系统的投播框架可以解决鸿蒙设备和非鸿蒙设备间媒体数据流转能力，如：分布式相机视频流流转到安卓系统展示；使用安卓系统电视作为鸿蒙分布式目标显示设备进行投屏等；
可以在鸿蒙设备间实现分布式相机及分布式屏幕多跳预览，可以新增鸿蒙设备间分布式媒体播放，分布式音视频聊天等；

## 8 编程规范
代码规范遵从OS社区C++语言编程规范，其中另行约定如下：

- 宏定义、函数名、类名、变量名、枚举等使用单词不能超过5个，'_' 或驼峰方式都是如此；
- 事件命名：EVENT_接收模块_主体_操作， 如： EVENT_MEDIA_CONSUMER_STOP；
- 状态事件命名：EVENT_接收模块_STATE_主体_操作， 如：EVENT_AGENT_STATE_PROSUMER_CREATE；
- 错误码命令：ERR_模块_操作_分类（可选），如：ERR_CONTEXT_CREATE；
## 9 框架反射机制
### 9.1 介绍
由于投播框架需要在控制层和媒体层上，支撑使用任意方式获取媒体数据和发送媒体数据。这些差异性，在这里，称之为业务实现。
框架如何支撑支持各类业务？答案是使用反射机制。
投播服务在启动和运行期间并不知道采用哪种业务实现方式处理，而是通过业务自行决定。为此框架采用反射机制用来支持这种灵活性。
反射：其实就是通过类的名字（类名是string）来获取类的实例，在运行时加载、探知、使用编译期间完全未知的class。例如：在创建agent时可以指定具体的session实现类名称，由agent根据类名称去实例化具体session类。
### 9.2 实现
```cpp
namespace Sharing {
using Constructor = std::function<std::shared_ptr<void>()>;

//反射实现类
class ReflectRegistration : public Singleton<ReflectRegistration> {
    friend class Singleton<ReflectRegistration>;

public:
    std::shared_ptr<void> CreateObject(const std::string &descriptor);
    bool Register(const std::string &descriptor, Constructor creator);
    void Unregister(const std::string &descriptor);
    ~ReflectRegistration();

private:
    ReflectRegistration &operator=(const ReflectRegistration &) = delete;
    ReflectRegistration &operator=(ReflectRegistration &&) = delete;
    std::mutex creatorMutex_;
    std::unordered_map<std::string, Constructor> creators_;
};

//注册函数名和实例化函数
class ReflectClassRegister {
public:
    ReflectClassRegister(const std::string &name, Constructor func)
    {
        ReflectRegistration::GetInstance().Register(name, func);
    };

private:
    ReflectClassRegister() = delete;
};

//向框架注册业务实现类
#define REGISTER_CLASS_REFLECTOR(className)                \
static std::shared_ptr<className> className##Creator(void) \
{                                                          \
    auto obj = std::make_shared<className>();              \
    obj->SetClassName(#className);                         \
    return obj;                                            \
}                                                          \
const ReflectClassRegister className##Register(#className, className##Creator)

template <class T>
class ClassReflector {
public:
	///根据类目实例化类
    static std::shared_ptr<T> Class2Instance(const std::string &name)
    {	
        return std::static_pointer_cast<T>(ReflectRegistration::GetInstance().CreateObject(name));
    };
};
} // namespace Sharing
```
## 10 框架事件驱动
### 10.1 介绍
交互、业务容器、媒体通道等模块是投播框架中最核心的模块，它们之间相互解耦。
这些模块之间如何交互？答案是事件消息处理。不同模块之间发送事件都是发到模块的管理实例中，然后由模块管理实例一步步处理。
### 10.2 事件路由
事件如何从一个模块发送到另一个模块？答案是通过调度中心转发。
事件消息都继承一个公共地址结构EventMsg，该地址结构包含了模块发送端和目的端的管理类Id和模块实例Id，而这些id就是模块各个实例的地址门牌号。调度中心根据这些id，把事件路由到不同的模块管理类实例中去处理，如：
```cpp
struct FromMsg {
    using Ptr = std::shared_ptr<FromMsg>;
	uint32_t fromMgr; //模块管理类Id;
	uint32_t srcId; //模块实例Id, 如contextId，mediachannelId
};

struct ToMsg {
    using Ptr = std::shared_ptr<ToMsg>;
	uint32_t toMgr; //模块管理类Id;
	uint32_t dstId; //模块实例Id, 如contextId，mediachannelId
};

struct EventMsg: public FromMsg, 
				 public ToMsg {
	virtual ~EventMsg() = default;
    using Ptr = std::shared_ptr<EventMsg>;
    EventType type; //事件类型
	bool sync;
};
```
### 10.3 事件流转
模块管理类率先接收并处理接收到的事件消息，如果不是自己的事件，则根据模块实例id号，将该事件传递到相应的模块实例中；模块实例处理自己的事件，如果不是自己的事件，则将事件传递给相应的业务实例中继续处理。
### 10.4 事件权限
#### 10.4.1 关键数据结构说明
事件消息全都继承EventMsg，区分框架事件和业务事件，其中：

- 模块实例：框架各模块及其管理类实例；
- 业务实例：BaseScene、BaseSession、BaseProducer和BaseConsumer派生类实例；
- 框架事件：模块实例接收或发出的事件。
- 业务事件：业务实例接收或发出的事件，由业务实例定义和解析，框架负责转发和送达，不解析事件。
#### 10.4.2 事件发送职责与权限：

- 只有模块实例才具备事件发送权限；
- 模块实例操控所属业务实例，只能通过业务实例的接口函数实现；
- 模块实例可以向其他模块实例发送框架事件，但不能向业务实例发送框架或业务事件；
- 模块实例和其他模块所属业务实例交互，可通过向该业务实例所属模块实例发送框架事件，模块实例接收事件后调用所属业务实例接口来实现；
- 业务实例只能接收处理业务事件，也可以构造业务事件；
- 业务实例不具备发送事件权限，但可以委托其所属模块实例来发送业务事件；
- 业务实例只能向其他业务实例发送事件，不能向模块实例发送事件。那么问题来了，业务实例如何将状态、数据通知给所属模块实例呢？答案是通过注册回调方式来实现。
### 10.5 处理机制
框架如何支持事件并发？答案是由事件中心的线程池和队列来解决。
事件中心有一个线程池和任务队列，异步情况下，发送模块将事件插入到任务队列尾部后返回，事件管理从线程池中选择一个空闲线程去处理任务队列头部的任务。同步情况下，发送模块将事件直接插入到任务队列头部，并等待执行结束后返回。
## 11 业务定制部分
投播服务分为投播框架部分和业务定制部分，这两部分共同完成业务的功能需求。框架为业务定制部分设计了固定的行为准则、状态机制，事件消息交互流程及步骤，开放并限定了业务定制部分的权限和能力，使得框架模块和业务定制部分责权清晰，深度结合，解决了框架适配业务差异性的问题。业务定制部分如下：

- Scene：交互模块的定制部分，实现不同业务场景的服务接口层逻辑。
- Session：业务代理的定制部分，实现业务代理Agent的信令控制层处理逻辑。
- Consuer：媒体层获取媒体数据的定制部分，实现业务代理Agent的媒体层处理逻辑。
- Producer：媒体层输出媒体数据的定制部分，实现业务代理Agent的媒体层处理逻辑。

## 4 实现设计
### 4.1 事件通知机制
#### 4.1.1 关键功能实现说明
（1）事件发送端Emitter：
事件发送端不进行注册，仅通过访问EventManager的PushEvent接口向管理类中添加数据
（2）事件监听器Listener：
事件监听器Listener需要向EventManager进行注册，注册前需要填写本监听器接受的事件，并在注册时进行订阅操作。所有继承事件监听器Listener的模块需要实现OnEvent事件处理函数。
（3）任务线程池TaskPool
线程池TaskPool管理一个线程列表，每个线程承载一个packaged_task，当task运行时，可以通过返回的std::future获取其任务处理是否超时。
（4）任务管理类EventManager
任务管理类继承TaskPool，同时内部管理事件队列和监听者map列表，启动后开始事件处理循环，当有Emitter通过暴露的接口向本类发送事件时，将根据事件类型，寻找到监听该事件的Listener，使用其OnEvent函数建立packaged_task, 返回future监听其是否运行超时。

# 四、业务容器
## 1 模块功能描述
### 1.1 业务容器
Context实例是管理一组有关联业务的Agent容器。根据流媒体播放业务需要，将不同类型的Agent组合关联在一起，用于实现媒体数据的获取、预览、处理、输出业务，每个Context实例可管理多个Agent实例。
### 1.2 业务代理
Agent是处理媒体数据获取或者输出业务的代理，Sink Agent专门处理媒体数据获取业务， Src Agent则用于处理媒体数据输出业务。Agent负责代理业务在框架内部交互，而具体的业务实现由Session承担。例如：Miracast协议的Sink端投屏流，本地文件流、屏幕采集流、分布式相机流的获取都在Sink Agent中实现，Miracast协议Source端在Src Agent中实现等。
Session是与Agent绑定的业务实现部分，是媒体数据获的获取和输出在控制层的实现，由框架使用者实现；例如：miracast、softbus、rtsp、onvif、sip等协议交互部分。

### 4.1 容器管理
#### 4.1.1 关键功能实现说明
ContextMgr容器管理用于管理框架所有的业务容器，提供业务容器的增、删、查、改功能； ContextMgr接收所有业务容器模块的事件，并根据事件目标地址分发到各个实例中去处理。
Context作为Agent的管理容器，构建和掌管一组相关联的Agent，根据业务需要，可以包含不等数量的Sink Agent和Src Agent，Context实例管理Agent相关事件构建和分发，状态更新与销毁。
Agent作为业务代理类，代理业务控制着媒体数据处理的统一流程，其绑定的Session实例用于实现控制层逻辑处理，通过事件消息操控MediaChannel对象的Prosumer实例，则是用于实现媒体层逻辑处理。所以，对于使用投播框架的外部程序来讲，仅知道业务代理Agent的存在，并不知情投播框架内部，业务在信令控制层和媒体处理层是分离的。Agent对象不仅控制媒体通道的创建，Prosumer对象的创建，还操控Prosumer对象的运行时状态，以及媒体数据的预览等。
在创建Agent实例时，会同步创建业务定制部分的实例，这些业务定制部分的实例和框架实例共同完成所需业务功能。框架实例通过绑定业务定制部分的实例，完成了框架和业务的结合。

# 七、通道管理
## 1 模块功能描述
通道管理模块，用于管理媒体通道的添加、删除、修改、查询。媒体通道是媒体数据获取和输出业务在媒体层的实现，掌管媒体资源的获取，播放、混流与输出，并且可以对媒体数据进行封装与解封装、拆包与组包 。媒体通道包含MediaChannel和MixChannel两种通道类型。
Mediachannel通道主要用于媒体资源的获取，预览和输出功能。每个MediaChannel通道的媒体资源通常只包括一路音频和一路视频或其中之一。媒体资源的获取与输出并不限定实现方式，这部分由Consumer和Prosumer实例来实现。Consumer对象用于获取媒体资源，获取方式根据业务需要来指定，例如通过网络协议拉取方式、本地文件或共享文件读取方式、本地设备或分布式设备读取方式，共享内存读取或管道读取等。Prosumer对象用于对外输出媒体资源，输出方式根据业务需要来指定，例如通过网络协议推流方式、管道输送方式，共享文件方式，协议透传方式等；
MixChannel通道主要用于多路媒体资源的处理，例如对多个MediaChannel通道的媒体资源进行混屏播放，混流发送等。其中，混屏播放将多路视频帧合为一帧图像用于窗口预览；合流转发则将多个媒体资源通过单端口合并后发送；

### 2.2 环形通知队列
#### 2.2.1 功能描述
##### 2.2.1.1 主要功能

- 支持一方写入多方读取，互不干扰；
- 队列可写入音频数据和视频数据；
- 使用节点数据清除策略，队列长度可弹性可收缩；
- 环形队列内部音视频数据节点同步且有序；
- 队列写入音频和视频数据相互对立；
- 队列提供内存申请和释放机制；
- 队列支持单一读取音频和视频数据；
- 队列支持按时间轴读取音视频数据；
- 最大支持16路读取者的读取操作；
- 读取者可主动获取数据和被动读取数据；
##### 2.2.1.2 方案价值
优点：

- 用户读取时不需要为音频或视频数据建立缓存，节省内存使用；
- 可单独获取音频，过滤不需要预览的媒体通道视频数据；
- 可单独获取视频，满足静音要求过滤不需要的音频数据；
- 可独立获取音视频数据，满足独立播放声音和预览视频需求；
- 提供内存申请接口，使用者可直接写入音视频数据，避免插入队列时的拷贝；
- 内有空闲队列，避免每次写入数据时申请内存，提高性能；

缺点：

- 音频视频串行写入，造成队列长度较长，如果旧数据释放不及时，内存使用较高；
- 节点删除策略复杂，音频视频节点计数单独维护，开发难道大，故障率高；
##### 2.2.1.3 专业术语
| **关键词** | **详述** |
| --- | --- |
| 关键帧批量删除 | 在写入数据时，当遇到关键帧写入会自动触发批量删除该关键帧之前所有帧操作，由于环形队列可拥有多个读用户，因此为了保证每个用户读取数据正常，批量删除操作遇到未读节点，自动终止；换言之，该关键帧之前的所有已读数据全部删除。使用范围是（0，队列长度最大值）。 |
| 队列最大值删除 | 在队列长度达到队列长度最大值时，节点插入的同时，必须删除旧节点，旧节点删除策略参考2.3.3。 |
| 数据单元 | 一个由音频帧或视频帧裸数据构成的存储结构。由写入者申请，所有权在调用环形队列写数据接口时转移。 |
| 空闲队列 | 简称空闲队列，由数据单元节点构成。环形队列拥有两个空闲队列分部存储音频数据和视频数据。 |
| 顺序读取 | 读取队列数据的方式，不需要指定读取数据类型（音频和视频），环形队列内部按插入顺序依次返回数据及类型； |
| 按类型读取 | 读取队列数据的方式，需要指定读取数据类型，环形队列内部按照写入顺序依次返回对应数据类型的数据； |
| 数据游标 | 环形队列为每个读取者建立一套数据节点索引，包括音频索引和视频索引，用以标识读取者在环形队列中音频和视频的读取位置；每个读取者的数据游标相互独立； |
| 队列长度 | 环形队列的队列长度N，在纯音频节点的情况下，队列长度N为配置初始值，队列长度最大值为配置最大值。在自动配置N结束时，如果队列长度N大于配置最大值，则队列长度N为配置初始值，队列长度最大值为配置最大值；如果队列长度N小于配置最大值，则队列长度N为当前值，队列长度最大值为min(队列长度N*2，配置最大值)； |
| 队列模式 | 以队列存储的所有数据节点类型为判断依据，分为单一模式和混合模式； |
| 单一模式 | 队列长度达到队列长度最大值时，队列中的所有数据节点类型相同，如纯音频或纯视频节点； |
| 混合模式 | 队列中有音频节点和视频节点； |
| 读通知标志 | 无符号32位整形原子变量，是通知线程和读取线程共同操作的一个标志。区分音频位和视频位，可标识16路读取者的可通知状态。 |
| 可读标志 | 无符号32位整形原子变量。区分音频位和视频位，可标识16路读取者的音频或视频可读状态。 |
| 正向通知 | 环形队列的通知线程向读线程发送一次信号通知，解锁读线程进行一次数据单元的读取操作；读取线程在未收到通知信号前处于锁死状态，收到正向通知信号后，自动解锁进行一次读取操作； |
| 反向通知 | 读取线程完成当前的一次数据单元读取操作后，根据环形队列该读取者的可读标志，可向通知线程发送信号，用于触发新的一轮正向通知。 |
| 通知线程 | 环形队列的常备线程，用于对所有读取者进行读取正向通知。每完成一轮对所有读取者的读取正向通知后，自动进入锁死状态，等待读线程或写线程的反向通知解锁，解锁后进行下一轮读取正向通知。 |
| 读取控制权 | 控制着环形队列数据单元的读取节奏，也就是谁来控制读取操作。可以是环形队列的通知线程，也可以是读取者的线程。 |

#### 2.2.2 技术要求

- 自动配置N策略执行过程中，当视频gop值确认时，队列长度N值确认为gop大小的1.2倍长度；
- 队列长度N既有配置初始值也有配置最大值，当自动配置N策略执行中或自动配置N策略结束时，如果2N大于配置最大值，则队列长度最大值采用配置最大值，否则队列长度最大值为2N；
- 自动配置N策略默认启用，配置最大值生效意味着自动配置N策略失效；
- 支持单独读取音频或视频数据，也支持按时间轴获取队列节点数据。
- 每个读取者拥有独立的一套数据游标，区分视频数据游标和音频数据游标；
- 不同用户之间数据游标相互独立，互不干扰；
- 环形队列提供内存申请接口，内存结构称为数据单元，用户在组包或者读取数据时使用该数据单元，在写入数据时转移数据单元所有权，避免写入时的数据拷贝；
- 环形队列维护两组数据单元空闲队列，分别为视频空闲队列和音频空闲队列；数据单元空闲队列初始为空，环形队列节点删除时根据策略将数据单元节点插回到对应空闲队列中。
- 数据单元空闲队列长度不需单独限制，当队列长度大于队列长度N时，删除队列节点中的数据单元直接删除；当队列长度小于等于队列长度N时，删除队列节点中的数据单元插回到空闲队列；
- 模式判断：队列内部记录音频节点和视频节点数量，当队列长度等于队列长度最大值时，触发模式判断，以所有节点是否为同一类型作为判断依据确认队列模式。如果为单一音频模式，队列长度N和队列长度最大值均采用配置值；
- 单一音频模式切换混合模式。在单一音频模式下，如果突然写入视频数据，触发切换混合模式，则清空队列并触发自动配置N策略执行，队列长度N取max(自动配置N确认时数值，配置默初始值），队列长度最大值取min(队列长度N*2，配置最大值)。
- 混合模式切换单一音频模式：在混合模式下，在队列当前长度达到队列长度最大值时，判断队列节点类型是否全音频，如果全为音频节点，则重新确认队列长度N和队列长度最大值；此时，队列长度N取配置初始值，队列长度最大值取配置最大值。
- 单一模式和音视频模式影响的是队列长度N和队列长度最大值取值；对应的删除策略也略有不同，具体参照2.3.3。
- 环形队列写操作时，必须保证音视频同步，单一类型数据时间顺序递增。
#### 2.2.3 删除策略
##### 2.2.3.1 删除方式
队列节点删除方式区分关键帧批量删除和队列最大值删除。

- 在自动配置N策略执行中，当遇到视频关键帧写入时，触发关键帧批量删除操作；
- 在自动配置N策略执行结束时，队列长度N和队列长度最大值已经确认。如果队列模式为单一视频模式或者混合模式，写入视频关键帧时，会触发关键帧批量删除操作；
- 如果队列长度已经达到队列长度最大值，如果写入的数据是视频关键帧，先触发关键帧批量删除，如果批量删除失效（没有数据节点被删除），再触发队列最大值删除；如果写入的数据是非视频关键帧数据，则采用队列最大值删除。
- 队列最大值删除时，如果写入的数据是音频数据，则采用插一删一方式；如果写入的数据是视频数据，则采用插一删多方式，即找到最旧视频节点，删除该节点及比该节点旧的所有音频节点（如果有），如果没有找到最旧视频节点，则删除所有音频节点，参照单一音频模式切混合模式。
##### 2.2.3.2 场景分类
| **关键词** | **详述** |
| --- | --- |
| 只写不读 | 使用关键帧批量删除方式，删除写入关键帧之前的所有数据，如果当前队列长度小于队列长度N，删除的数据单元节点插回到对应的数据单元空闲队列中，如果当前队列长度大于队列长度N，直接删除该队列节点。 |
| 一写一读 | 当前队列长度在队列长度N以内时，遇到关键帧写入触发关键帧批量删除；当队列长度在[队列长度N, 队列长度最大值)时，策略同当前队列长度在队列长度N以内，不同点是删除的节点直接释放；当前队列长度等于队列长度最大值时，通常采用队列最大值删除方式，如果写入的是视频关键帧，则先触发关键帧批量删除，如果没有节点删除再触发最大值删除。 |
| 一写多读 | 队列长度在队列长度N以内时，遇到关键帧写入触发关键帧批量删除，删除所有用户已使用过的视频节点及其之前所有的音频节点；当队列长度在[队列长度N，队列长度最大值)时，策略同当前队列长度在队列长度N以内，不同点是删除的节点直接释放；当队列长度在队列长度最大值时，采用队列最大值删除方式，如果找到的最旧视频节点有部分用户未使用，则强制删除。 |

注：队列音频节点长度不敏感，主要控制视频节点长度，换言之，当队列长度达到最大值时，多数是视频读取比音频读取慢的场景；在音频读取比视频慢的情况下，对于音频播放来讲属于不正常现象，以bug解决来处理。
##### 2.2.3.2 极端场景

- 弱网环境下接收音视频流，在视频写入慢音频写入快的情况下，自动配置N策略执行过程中，队列长度N大概率会达到配置最大值，此时队列最大值删除如果只按照插一删一策略，会导致队列长度长期等于队列长度最大值，此时队列大部分数据是音频，导致视频解码异常和播放卡顿；
- 正常环境下，视频音频写入相对稳定。如果视频读取比音频读取慢，假设非其他用户读取慢拖后腿的情况下，音频正常消费，视频缓慢消费或不消费，此时应主要删除视频节点，在这些视频节点前的音频节点全部删除，因为音频早已消费；
- 正常网络环境下，视频音频写入相对稳定。如果视频读取比音频读取快，理论上不存在，除非音频播放线程不工作，或者处于静音模式不播放，这种情况队列长度达到队列长度最大值时，删除最旧视频节点，也应该删除视频节点前的所有音频节点，因为音频早已不需要再消费。
- 音频写入比视频慢的情况，理论上只有采集异常时候，这种场景引起的异常当做bug解决，删除策略也是删除视频节点，在该视频节点前的音频节点理应删除；
- 当音频数据读取很慢，队列长度达到队列长度最大值时，队列里面大部分是音频数据，此时队列中的视频gop难以保证，需要删除队列节点以满足视频数据写入需要，在这种情况下，把需要删除的视频节点删除，同时在该节点之前的音频节点也全部删除；
#### 2.2.4 使用要求
##### 2.2.4.1 写入要求
环形队列仅支持一个用户写入，写入时无论是音频数据还是视频数据必须保证音视频同步，音频或视频时间戳顺序递增。如果需要写入音视频数据，在队列长度达到队列长度最大值之前，必须写入音频和视频数据，否则环形队列模式为单一模式，会对队列长度N和队列长度最大值产生影响。另外，当队列感知模式切换时，会清空队列，触发自动配置N策略执行。
##### 2.2.4.2 读取要求
环形队列支持多用户并行读取。读取接口区分顺序读取和按类型读取。

- 顺序读取主要用于推流、封装时使用。使用方建议单线程读取；
- 按类型读取主要用于视频预览与音频播放。使用方可双线程读取，互不干扰；
#### 2.2.5 读取驱动模式
##### 2.2.5.1 播放预览模式
适用于应用层创建视频窗口，框架层在此窗口上进行视频预览。此时，环形队列接手数据单元读取控制权，主动通知读取线程读取音频或视频帧数据。在读取线程读取完一帧数据后，读通知标志位复位，允许环形队列通知线程正向通知读取线程进行下一次的读操作。同时，如果环形队列还有该用户未读完的数据单元（根据可读标志），则反向通知环形队列的通知线程，进行下一轮的读线程正向通知操作。此时，读取线程自动进入锁死状态，等待通知线程的下一次正向通知。
本模式自动促使新增读取者的读数据追赶操作，直到读完最新数据单元后进入锁死状态为止。经过一小段时间后，环形队列所有读取者的读取位置基本相同，都为最新数据 。
##### 2.2.5.2 混流预览模式
适用于框架层自管理视频预览窗口，此模式下，数据单元读取控制权在读取线程中，由读取线程控制每帧数据的读取节奏，一般用于混流预览。如果读取线程读取数据单元太慢，环形队列触发的删除操作会造成读取数据单元不连续，造成解码花屏。

#### 4. 1. 1 关键功能实现说明

# 十、进程交互
## 1 模块功能描述
交互模块Interaction主要用于实现设备内和设备间的跨进程通信。对上提供一套框架级C++接口，供业务实现类Scene实例调用，封装出具体业务的NAPI或CAPI接口。Interaction实例和Scene实例是一一对应绑定关系，共同完成对外交互和对内操控。投播服务与客户端，跨设备投播服务之间的交互都是基于 IPC与RPC机制实现。投播服务支持与多个客户端进程并发交互，不同客户端进程与投播服务之间的交互数据彼此隔离。
Interaction manager管理所有interaction实例。交互模块接收到的所有事件均由interaction manger接收并分发给各个interaction实例；通知接口层的事件则由Scene实例处理并上报客户端。

### 4.1 数据中心
#### 4.1.1 关键功能实现说明
数据中心模块采用单例模式，通过模块间事件交互获得数据并存储到数据库中。其它模块通过事件中心发送事件来上报数据，数据中心接收事件并存储数据。数据中心内部存储数据可使用KVStore数据库进行分布式设备数据通信。也可以使用RdbStore来存储数据。数据中心是投播框架数据查询的唯一入口。
# 十二、配置中心
## 1 模块功能描述
系统配置模块，对文件IO操作，读写配置文件，并保存到内存中，可按key、按模块、按模块标签方式获取配置数据。配置数据在服务拉起时加载，区分框架配置数据和业务配置数据。模块包含框架模块和NAPI模块。配置数据有效原则如下：

- 当配置数据有效时，以配置数据为准；
- 当业务配置数据和框架配置数据冲突时，以框架配置数据为准；
- 当配置文件不存在时，已框架默认数据为准。

## 4 实现设计
### 4.1 配置中心
#### 4.1.1 关键功能实现说明
配置中心是配置数据落盘与加载的模块。目前采用单例模式，框架和业务对象可根据需要查询、获取所需数据。后续若上升到模块级别，需独立收发事件，并将配置信息推送到相关模块。也可用接收事件来更新配置数据，并将其写入到配置文件中。

# 十三、 附件
## 错误码
### 功能描述
通过使用标准的错误码定义和格式，我们可以更好地识别和处理系统中的错误，提高系统的可维护性和可靠性。投播框架对外错误码是由188开始的八位纯数字组成，分为四个部分用于表示错误发生的服务或子系统、具体的错误类型和错误发生的位置或来源。具体分配如下：

- 第1-3位：部件代码。188用于表示投播框架服务。
- 第4-5位：模块代码。用于表示错误发生的模块或子系统。采用两位数字表示，从00开始递增。不同的模块或子系统对应的代码不同。
| 00 | 投播框架 |
| --- | --- |
| 01 | 音视频通话SDK |
| 02 | 投屏SDK |
| 03 | 流播放器 |
| 04 | 推流器 |

- 第6-6位：错误来源。用于表示错误发生的位置或来源，用于内部分类，可按模块、功能等划分，例如

框架层可划分为：

| 0 | 默认 |
| --- | --- |
| 1 | 交互模块 |
| 2 | 业务容器 |
| 3 | Session |
| 4 | 媒体通道 |
| 5 | Prosumer |
| 6 | 编解码预览 |

NDK对外只暴露业务层概念，不暴露媒体通道层，故不需要设置媒体通道类型分类，NDK可划分为：

| 0 | 默认 |
| --- | --- |
| 1 | Sink端 |
| 2 | Src端 |
| 3 | 预览 |
| 4 | 转码 |

- 第6-8位：错误代码。用于表示具体错误。例如投播框架业务模块中错误代码定义：
| 01 | context创建错误 |
| --- | --- |
| 02 | agent创建错误 |
| 03 | agent启动错误 |

### 错误码样例
8位错误码示例为：188 00 1 01。其中，第1-3位表示投播框架服务；第4-5位表示该错误发生在框架层；第6位表示子模块为框架业务模块；第7-8位表示该错误来源于业务容器创建错误。
